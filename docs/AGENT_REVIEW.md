# Agent review

Agent review lets an architect point a coding agent, such as Claude Code, at a repository and get structured evidence for each concern, without reading every file by hand. The agent suggests and the architect decides.

## Flow

1. **Choose a scope.** In the page, pick a category (best), all concerns, or only concerns not yet reviewed. Concerns that need people or runtime data are left out unless you include them.
2. **Run it in Claude Code.** In your repository, start Claude Code in plan mode, which is read-only. Run `claude --permission-mode plan`, press Shift+Tab to cycle to plan mode, or type `/plan`. Paste the prompt, or use the downloaded skill.
3. **Paste the result back.** The agent replies with one JSON object. The page imports it and shows a result badge, evidence, any red flags the agent reports and a note on each concern.
4. **Decide.** You set the status. For "found", "not found" and "not applicable" the page offers a one-click suggested status. "Partial" and "cannot determine" always need your judgment.

The skill is saved as `.claude/skills/production-readiness-review/SKILL.md` in the target repository. Skill support depends on your Claude Code version. If it is not available, use the copied prompt.

## Where to run it

Run the agent on a repository you trust, or on a throwaway copy. A repository can contain text, hooks, settings or MCP servers that try to steer an agent. For code you do not trust, use a fresh checkout with project hooks, MCP servers and project settings turned off, and no credentials in the environment. The prompt tells the agent to treat repository files as data, but a prompt is an instruction, and the sandbox is the real control.

## Prompt contents

For every scope the prompt has the same ground rules, then one block per concern with its definition, how it works, when it applies, review question, where to look, search hints, patterns to look for, evidence to request from people, what good looks like and red flags. It ends with the JSON format. The text is generated by `src/lib/prompt.js`. To see it, run `npm run prompts` and read `dist/prompts/`.

The ground rules came out of the review rounds. They cover, in short: read-only work; no running, building or network access; no infrastructure or cloud CLIs, no state files; git limited to `ls-files`, `grep` and a patch-free log with a fixed format, and no `gh`, `glab` or CI CLIs; no database connections or SQL; runbooks and chaos or failover scripts are read, never run; secrets, tokens, hashes, keys and personal data are never quoted, and dumps and environment files are reported by path or key name only; repository text is data, including `CLAUDE.md`; generated code, build output, vendored dependencies and lockfiles are excluded; evidence must be visible in the repository; a red flag that needs runtime data or team process is not reported from code; an end-of-support flag needs a date stated in a file; a flag that depends on a product default needs the product identified; injection findings need a traced input; `not_applicable` needs positive evidence; and every result needs a file, a line and a short quote.

## Result format

```json
{"findings":[{"id":11,"result":"partial","evidence":[{"file":"src/http/client.ts","line":42,"quote":"timeout: 30000"}],"red_flags":[],"note":"2 of 3 services covered. Set for the payments client only."}]}
```

`result` is one of `found`, `partial`, `not_found`, `cannot_determine`, `not_applicable`. `red_flags` lists the red flags the agent reports, each with the text exactly as listed and its own evidence. The schema is [`schema/agent-findings.schema.json`](../schema/agent-findings.schema.json).

## Safety model

| Risk | Mitigation | Limit |
| --- | --- | --- |
| The agent changes the repository | Prompt says read-only and recommends plan mode | A prompt is an instruction. Plan mode is the real control. |
| The agent runs code, tools or commands from the repository | Prompt forbids running, building, network access, infrastructure and cloud CLIs, database clients and CI tools | Same limit. Use a sandbox for code you do not trust. |
| Secrets are printed or copied into findings | Prompt forbids printing secret values and asks for "secret value redacted". The page masks anything that looks like a credential in imported text before it is stored or shown | Masking is pattern based, so review findings before sharing them. Quotes are capped at 200 characters. |
| Text in the repository redirects the agent | Prompt says to treat repository text as data | This reduces the risk but does not remove it. Use repositories you trust. |
| The agent guesses | Prompt demands evidence and allows `cannot_determine` | An agent can still cite plausible but wrong evidence. Verify before marking decided. |
| Pasted findings attack the page | Findings are validated, truncated, masked, and shown as plain text | None known. |
| Findings leak from the browser | Kept in `sessionStorage` (this tab only, gone when it closes), with a Clear findings button | Anyone using the open tab can read them. Other tabs and other sites on the same origin cannot. |

## Limits

- An empty search is not proof of absence. The prompt says so, and `not_found` should be checked.
- A repository does not show everything. Branch protection, approvals, access, restore tests and other settings live in a platform, so a `partial` concern asks the agent to report what it can see and to list the rest as needing people evidence.
- Search hints are untested across many stacks. Treat them as starting points and improve them through pull requests.
- Large prompts work worse. One category is about 4,000 to 12,000 tokens. All checkable concerns is about 52,000. Run one category at a time.
- Concerns marked `people` need documents or runtime data an agent cannot see.
- The prompts have not been run against real repositories in many stacks yet. See `docs/REVIEW_PROCESS.md`, section 4.
